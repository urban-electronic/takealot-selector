# 补货列表逐商品查资格：总览 318 条、待办 317 条 SQL（2026-10-27）

上一处同类问题见 [调价列表逐条查档案](2026-10-27-pricing-listing-n1.md)。两处都是
「列表循环里调了一个只判断单个商品的函数」，但根因在不同 helper，按一个改动一个缺陷
分开处理。

## 现象与证据

补货页首屏两个请求，本地库 329 个商品（SQLAlchemy `before_cursor_execute` 统计）：

| 接口 | 修复前 SQL 条数 | 修复前耗时 |
| --- | --- | --- |
| `GET /api/operations/overview` | 318 | 66.1ms |
| `GET /api/operations/alerts` | 317 | 63.5ms |

查询数 ≈ 商品数，说明每个商品都单独查了一次。

## 根因

`services/seller_operations_sync.py` 的 `eligible()` 只判断一个商品：

```python
def eligible(db, store, product):
    if product.link_status in ('已购买', '已上架'):
        return True
    return db.query(ProcurementRecord).filter(...).first() is not None
```

它在三个循环里被逐条调用：

- `api/operations_routes.py` 的 `overview()`（补货总览）
- `api/operations_routes.py` 的 `alerts()`（待办）
- `services/seller_operations_sync.py` 的 `apply()`（每小时卖家同步的落库循环）

## 改法

| 位置 | 改动 |
| --- | --- |
| `services/seller_operations_sync.py` | 新增 `eligible_ids(db, store)`：两条聚合查询（链接状态命中 + 有非取消的有效采购）算出全店可补货的商品 id 集合 |
| `api/operations_routes.py` | `overview()` / `alerts()` 循环前取一次集合，循环里只做 `p.id not in can_replenish` |
| `services/seller_operations_sync.py` | 同步 worker 的落库循环同样改用集合 |
| `tests/test_operations_routes.py` | 新增守卫：3 个与 60 个商品各跑一次，断言 SQL 条数不增长 |

`eligible()` 本身保留不动：`get_profile()` 和单商品路径还在用它，语义没变。

## 验证

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| `overview` SQL 条数 | 318 | **6** |
| `overview` 耗时 | 66.1ms | **9.1ms** |
| `alerts` SQL 条数 | 317 | **5** |
| `alerts` 耗时 | 63.5ms | **8.5ms** |

- **输出等价**：造一份带采购记录与档案的库（已购买、有效采购、已取消采购、数量 0、
  已归档五种情况），新旧实现 `overview()` / `alerts()` 返回的 JSON 完全一致
  （4 行、2 条待办，取消/零数量/归档均未计入）。
- **反向探针**：把 `overview` 改回逐条 `eligible()`，守卫转红——
  `SQL 条数随商品数增长：3 个商品 13 条，60 个商品 70 条`。

## 守卫第一版是假绿

第一版 fixture 把所有商品都设成 `link_status='已购买'`，于是 `eligible()` 直接返回
`True`、一条查询都不发——旧实现也能通过，反向探针跑完毫无反应。改成「商品不设链接状态、
靠有效采购记录命中」之后条数才真正随商品数增长（13 → 70）。

教训：**比「SQL 条数」这类间接指标时，fixture 必须落在被测分支上**，否则测的是另一条
路径。反向探针的价值就在这里——它不看断言写得对不对，只看撤掉修复会不会红。
