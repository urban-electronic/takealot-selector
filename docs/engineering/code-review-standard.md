# 代码审查标准与流程（2026-10-27 起执行）

适用范围：`backend/`、`src/`、`scripts/`、`.github/`、`docs/` 的全部改动，包括本机 agent
的自动提交。本文与 [AGENTS.md](../../AGENTS.md) 是同一套规则的两个视角：AGENTS.md 写
「谁做什么」，本文写「按什么标准判定、按什么顺序做、什么情况算没做完」。

一句话版本：**一个 PR 只修一个可执行缺陷；门禁必须是本次改动的、全量的、跑在 head 上的；
测试必须能红；线上必须回读；写不清证据的改动不合并。**

---

## 1. 为什么要有这份标准

代码质量参差不齐，不是因为有人不会写，而是因为**「看起来绿了」和「真的对」之间有几处系统性
的缝**。这个仓库已经踩过的缝，每一条都在 `docs/engineering/` 里有记录：

| 踩过的缝 | 后果 | 记录 |
| --- | --- | --- |
| 采集任务卡在浏览器，等待期间还在刷心跳 | 线上采集全停 17 分钟，界面一直写「运行中」 | [采集看门狗](2026-10-20-collection-watchdog.md) |
| 四种读取失败原因共用一个文案 | 用户只看到「暂时无法读取」，只能反复点重试 | 同上 |
| 后端 naive UTC 序列化不带 `Z` | 前端按本地时区解析，时间整体早 8 小时 | [时间显示](2026-10-21-time-display.md) |
| 推送脚本只推 `HEAD^..HEAD` | 线上 ImportError（文件没上去） | 见 §6 发布纪律 |
| 用 `scrollWidth > clientWidth` 判文字溢出 | `text-overflow:ellipsis` 不改 `scrollWidth`，审计永远不红 | 见 §5 假绿清单 |

所以标准不写成「要仔细、要考虑周全」，而是写成**可判定的检查项**和**可复现的证据要求**。

---

## 2. 角色与职责

| 角色 | 职责 | 不做什么 |
| --- | --- | --- |
| 提交者 | 复现缺陷 → 改 → 自检 → 写 PR 证据 → 修审查意见 | 不在同一 PR 混无关重构；不重写别人分支；不把并行 agent 的未提交文件一起 `git add` |
| 审查者 | 按 §4 清单逐项判定，给出 P0–P3 结论与证据 | 不因风格偏好要求重写；不要求「先合并再修」P0；不接受旧门禁结果 |
| 合并者 | 确认门禁跑在 PR head 上、结论已解决、部署回读通过 | 不在 PR Check 红/缺失/过期时合并；不绕过签名与钩子 |

小团队里三个角色常由同一人兼任，**但步骤不能合并**：自己写的代码也要按 §4 过一遍，并且
至少换一次视角（隔一段时间或换一个 agent 再读 diff）。

---

## 3. 风险分级：审查深度按风险决定，不按代码行数

| 级别 | 范围 | 要求 |
| --- | --- | --- |
| **R1 资金与采集链路** | `backend/services/buybox_monitor.py`、`takealot_scraper.py`、`quote_browser.py`、`backend/api/pricing_routes.py`、任何影响成本/售价/利润计算的文件 | 双人（或两个 agent）复核 + **真实触发路径**复现 + 线上回读 + 回滚方案 |
| **R2 数据与状态** | 其余 `backend/`、导入导出、补货/库存/采购计算、店铺隔离、DB 字段与迁移 | 单人复核 + 边界与空值用例 + 存量数据兼容说明 |
| **R3 界面与交互** | `src/`、`src/index.css`、`scripts/test-*.py` 审计 | 单人复核 + 截图或审计脚本证据 + 多窗口尺寸 |
| **R4 文档与注释** | `docs/`、`README.md`、`AGENTS.md` | 自审 + 链接可点、与代码现状一致 |

判定取最高：一个改 `takealot_scraper.py` 又顺手改了文案的 PR 是 R1。

## 4. 必查清单

每条后面括号里是它存在的原因，不是修辞。审查意见必须指到具体条目编号（如 `C3`），
否则无法判定是否已解决。

### A. 正确性与范围

- **A1 一个 PR 一个缺陷。** 顺手重构、顺手格式化、顺手改文案都要拆出去（混在一起时，
  回滚一个 bug 会带走不相关的修复）。
- **A2 先复现再改。** PR 里要能读到「改动前怎么坏的」：命令、输入、页面、接口返回。
  没有复现记录的「防御性修改」不合并——它通常修的不是真正的原因。
- **A3 改动后重跑同一个触发路径**，不是只跑单测。单测绿而线上 ImportError 是这个仓库
  真实发生过的事故类型。

### B. 边界与空值

- **B1 0 / 空串 / null / 缺字段 各自代表什么，写清楚并全链路一致。**
  事故：参考价 `0` 被当成「已填」，列表显示 `¥0`、覆盖率算未填（MARKET-ZERO-01）。
  同一个字段有四处读取路径（`toPrice()`、`/status` 真值判断、`_to_price()`、
  `buildMarketBatch()`），改一处必须四处对齐。
- **B2 受控数字输入不能把非法值当清空。** 绑 `entry.price` 时敲 `0.5` 的第一个字符会清空
  输入框、最后存成 `5`。要留一份原文草稿，无效值只删草稿、不吞输入。
- **B3 空列表 / 空字典 / 首行为空 也要走到。** 表格、导出、聚合最容易在 0 行时崩或给出
  「全部正常」的假结论。

### C. 并发、超时与资源

- **C1 每个等待都要有上限。** `wait()` 无限等、`lock.acquire()` 不带 timeout、`with
  ThreadPoolExecutor` 隐式 `shutdown(wait=True)`，三者任一都能让整条循环停摆。
  现状基线：`JOB_TIMEOUT=240`、`shutdown(wait=False)`、`quote_context(wait_seconds=25/90)`
  超时抛 `CollectorBusy`。
- **C2 服务端预算必须小于客户端超时。** `src/remoteApi.ts` 默认 90s，交互式抓取
  `SCRAPE_BUDGET_SECONDS=75`。反过来会让用户看到一条与本操作无关的提示，而服务端还在跑、
  还占着采集锁。
- **C3 心跳不等于活着。** 刷新 `alive_at` 的循环本身可能就是卡住的那个。状态接口要能回答
  「上一轮到现在多久」（`cycle_age_seconds`），界面据此判断，不要只看 `worker_alive`。
- **C4 锁只在真拿到时释放**，异常路径也要保证不误放别人的锁。

### D. 失败可归因

- **D1 不允许 `except Exception: raise HTTPException(503, '暂时无法读取')`。**
  这类写法把密钥失效、限流、网络、代码报错压成一句话，用户只能反复重试。至少带异常类型或
  白名单类别（`_read_reason()`），且不透出路径、密钥、异常正文。
- **D2 状态码要区分「暂时」和「永久」。** 上游 5xx/超时 → 502/503 可重试；参数错 → 400；
  结构变化 → 需要人工介入的独立码。混在一起会让自愈逻辑误判。
- **D3 诊断字段只在真有错误时写。** 阶段成功但资料不全时 `err` 是空串，无条件
  `diagnostic(stage, err)` 会落成 `no_product_content`，把「被验证挡住」和「页面结构变了」
  混成同一件事——这两件的处理方式正好相反。
- **D4 落库前清掉上一轮遗留的计数/诊断**，否则自愈会把旧计数重判成本轮结果
  （COLLECT-DIAG-02）。

### E. 时间

- **E1 后端 `DateTime` 是 naive UTC，序列化不带 `Z`。** 前端 `new Date()` 会按本地时区
  解析，整体早 8 小时。展示一律走 `src/utils/datetime.ts` 的 `beijingDateTime()`，业务
  日期走 `todayLocal()`。
- **E2 服务端要落「用户看得见的日期」时**，显式
  `datetime.now(timezone(timedelta(hours=8)))`，不许裸 `datetime.now()`。
- **E3 前端不许出现不带 `timeZone` 的 `toLocale*`。**

### F. 安全与红线（违反即 P0，不讨论）

- **F1 不暴露密钥、cookie、浏览器 profile、真实账号信息**——代码、日志、PR 描述、截图都算。
- **F2 不绕过站点验证**：不解验证码、不伪装指纹、不换 IP、不伪造 UA 绕过风控。抓不到就如实
  报「安全验证未通过」，这是外部限制，不是缺陷。
- **F3 不开启真实调价、不改真实价格。** 需要改业务数据时，必须由用户明确授权范围并回读。
- **F4 测试只用隔离 fixture / 本地库**，不连线上库、不发真实卖家 API 写请求。
- **F5 不执行第三方脚本、不因为某个 skill 推荐就安装工具。** 先看范围、许可、副作用。

### G. 界面与可访问性

- **G1 用现有 token 与组件**，保持圆润紧凑、主操作清晰、高级说明折叠。没有需求不做重设计。
- **G2 视觉与可访问性有机器守卫**：`check-visual-consistency.cjs`、`test-contrast-audit.py`、
  `test-text-overlap.py`、`test-responsive-layout.py`（多窗口尺寸）、`test-longtitle-audit.py`。
  改了 `src/` 或 `index.css` 就要跑，且要跑**全量**（不要只挑一个尺寸）。
- **G3 截断/换行类改动的验证方式是读 computed style + 与容器右边对比**，不是看
  `scrollWidth`（见 §5）。
- **G4 中文主名 + 英文原标题并存时**，英文那行要 `nowrap + ellipsis` 且不撑破单元格
  （`REPLENISH-EN-01` 已有守卫）。

### H. 测试是否真的有效

- **H1 新断言必须能红。** 反向探针：临时撤掉修复（或改坏实现），确认该断言失败，再恢复。
  做不到这一步的断言只能算「记录当前行为」，不算回归保护。
- **H2 源码守卫要真的查注释里声称的规则。** `test-datetime.cjs` 头注释写了禁
  「`toLocale*` 不给 `timeZone`」，实现却只查 `getFullYear/getMonth/getDate`，于是一处机器
  时区写法混了十几轮。加守卫时对着注释逐条核。
- **H3 守卫要钉实现，不只钉行为。** 时区类测试在本机（UTC+8）会假绿：`datetime.now()` 与
  「UTC+8」断言相等，撤回修复也不转红。必须同时检查源码里不许出现裸 `datetime.now()`
  （`inspect.getsource` 含文档字符串，匹配前先剥掉）。
- **H4 fixture 要真的覆盖被测路径。** 未声明的接口会静默 404，页面停在空态，审计照样「通过」。

## 5. 假绿清单：这些「通过」不算通过

| 症状 | 为什么会假绿 | 正确做法 |
| --- | --- | --- |
| 审计 fixture 未声明某个接口 | 请求 404，页面空态渲染，没有元素可查 → 0 failure | 断言关键元素存在；接口缺失要显式失败 |
| `scrollWidth > clientWidth` 判文字溢出 | `text-overflow:ellipsis` 不改 `scrollWidth` | 读 computed `white-space`/`overflow-x` + 元素右边与容器右边对比 |
| `worker_alive: true` 就当采集在跑 | 等待循环本身在刷心跳 | 看 `cycle_age_seconds` 与 `last_cycle_at` |
| 时区测试在本机通过 | 开发机就是 UTC+8，断言与实现同错 | 同时钉实现（禁裸 `datetime.now()`） |
| `inspect.getsource` 里匹配到文档字符串 | 文档字符串也含示例代码 | `re.sub(r'""".*?"""', '', s, flags=re.S)` 后再匹配 |
| 只跑 `npm run check -- --quick` 就说全绿 | 跳过后端 pytest | 全量 `npm run check` |
| 门禁结果是上一个 commit 的 | PR Check 的 run 属于旧 head | 确认 run 的 SHA = PR head |
| 单测绿、真实路径红 | 单测没走入口、没走部署 | 复现同一个触发路径（§A3） |
| `git add` 后以为提交了 | 文件 stat 未变（行尾被归一）时会被跳过 | `git status` / `git show HEAD:path` 复核 |
| 「我改了但没测」 | —— | 这不是假绿，是未验证；PR 里必须写清未验证项 |

**量不到 ≠ 通过。** 审计项如果因为环境原因拿不到数值（例：`input[type=date]` 的字段在
shadow DOM 里，`:focus` 不匹配宿主，读到的 `outline` 必然为空，是假阳性），要单列
「量不到」，既不算通过也不算失败；一条可测的都没有时判失败。

## 6. 流程（提交者视角，按顺序，不许跳）

### 步骤 0：开工前对齐

```bash
git log --oneline -5
git status --short
```

工作区常有并行 agent 的未提交改动。看到不认识的改动不要清理、不要一起提交，只 `git add`
自己的文件。可选：`node scripts/review-brief.cjs` 会按改动文件列出本次该看哪几条清单、该跑
哪几个命令。

### 步骤 1：提交前自检（全量，不用旧结果）

```bash
npm run check          # 37 步：tsc / 视觉一致性 / 27 个前端套件 / 7 个审计 / 后端 pytest
```

- `--quick` 只跳后端，本地**验收**不许只跑它；只在「改的是纯前端且后端没动」的中间迭代里用。
- 任何一步红就停下，不要用「反正 CI 会跑」把红推给下一步。
- 结果要贴进 PR 的「验证」段：命令 + 关键行 + 通过数。
- 步数**不是常量**：`selfcheck` 扫 `scripts/test-*.cjs|mjs`（前端套件）与 `scripts/test-*.py`
  （审计）两个目录，放进去就自动纳入。写数字时先 `node scripts/selfcheck.cjs --list | wc -l`
  核一遍——本文初稿写的「24 个前端套件」就是凭印象写的，实际 27 个（2026-10-27 核对：
  2 + 27 + 7 = 36 步，加后端 pytest 共 37 步）。

### 步骤 2：反向探针（证明测试能红）

改动的断言逐条撤掉修复/改坏实现，确认它变红，再恢复。PR 里写清楚哪条断言、怎么撤的、红了
什么信息。没有反向探针的 PR，审查者按未验证处理。

### 步骤 3：自审 diff

```bash
git diff --cached --stat
git diff --cached
```

- `--stat` 出现「整个文件行数」级别的改动 = 行尾被改写，不是你的逻辑改动，先修掉。
- 逐行读。自审能拦掉大部分审查意见，也能提前发现误删（本轮真实发生过：批量替换误删了
  `.packing-product-en` 的规则）。

### 步骤 4：PR 描述（用模板，缺段不提交）

模板：`.github/pull_request_template.md`。必填段：触发路径 / 改动前复现 / 改了什么 /
怎么验证的 / 反向探针 / 风险与回滚 / 红线自查。

### 步骤 5：门禁必须是「本次的」

- PR Check 的两个 job（`Typecheck / visual / tests / build`、`Backend + layout tests`）都要绿。
- 绿的那个 run 的 head SHA 必须等于当前 PR head；红、缺失、过期三者都算未通过。
- 清单只在 `package.json` 的 `check` 里维护一份，**不要在 workflow 里手抄用例**——历史上
  `pr-check.yml` 和 `deploy.yml` 各抄一遍，两边都漏了用例。

### 步骤 6：审查结论

审查者逐条给 `A1…H4` 编号 + P 级 + 证据。结论只有三种：

- **通过**：0 个未解决 P0/P1。
- **需修改**：列出未解决项，每项写「哪一条、什么现象、怎么验」。
- **驳回**：违反 §F 红线、范围失控（一个 PR 多个缺陷）、或没有复现记录。

P2 允许延后，但必须留 TODO 或 issue；P3 只是建议，不得作为阻断理由。

### 步骤 7：合并与部署回读

- 推送用 `_push_diff_all.py`（按 `git ls-tree -r HEAD` 逐 blob 比对）。**不用**
  `_push_to_main.py`——它只推 `HEAD^..HEAD`，漏文件会直接导致线上 ImportError。
- 推完必须看它列出的文件清单：多出来的文件通常是行尾差异（内容零变化），要按远端原始字节
  恢复后重推，不要把它当成改动留下。
- 部署校验：`curl -H "Accept: application/json" <线上地址>/` 读 `build`，等它等于远端 main
  的前 12 位（不是本地 HEAD，本地没有服务端生成的 commit 对象）。
- 线上跑一次真实触发路径（不是只看首页 200）。

### 步骤 8：归档

| 写什么 | 写到哪 |
| --- | --- |
| 工程决策、根因、改法、口径约定 | `docs/engineering/YYYY-MM-DD-<主题>.md` |
| 逐轮复核、验收证据、未验证项 | `docs/review/YYYY-MM-DD-<主题>.md` |
| 长期有效的规则 | `AGENTS.md`（协作）或本文（判定标准） |

`docs/review/` 是逐轮记录，允许有「未验证」；`docs/engineering/` 是结论，只写已确认的事实。
不要把「未验证」写进 engineering 记录里冒充结论。

## 7. 审查意见的写法

好的意见长这样：

> **C1（P1，阻断）**：`_wait_with_heartbeat` 里 `wait(pending, timeout=10)` 外层是
> `while True`，没有退出条件，任务卡住时循环永不返回，且每 10s 刷 `alive_at`，界面会一直
> 显示「运行中」。证据：线上 `cycles=1995`、`last_cycle_at` 停在 17 分钟前、
> `worker_alive=true`。验证方式：把某个任务的 future 置为永不完成，`run()` 应在
> `JOB_TIMEOUT` 内返回并写 `collect_timeout`。

坏的意见：「这里写得不太好」「建议优化一下」「考虑一下并发」——无法判定是否已解决。

## 8. 例外与升级

- **紧急线上故障**：允许先修后补记录，但必须在同一个 PR 里补上复现与验证，且 24 小时内补齐
  归档；红线（§F）不因紧急而放开。
- **不确定是否属于缺陷**：先写成可复现的最小证据（命令/截图/接口返回），由审查者判定；
  不要用「防御性修改」代替定位。
- **标准与 AGENTS.md 冲突**：以 AGENTS.md 为准，并同步修本文——两份规则不一致时，实际执行
  的永远是更松的那一份。
- **标准本身要改**：改本文 + 在 PR 描述里说明「哪条规则造成了什么代价」，不要私下放宽。
