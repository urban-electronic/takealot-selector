# Buybox 调价模型：把「竞价雷达」的思路搬过来，不搬它的规则

参考物：`@user_2b384f75/ecommerce-price-radar`（v1.3.2，已安装到 `~/.workbuddy-ai/skills/`）。

那份 skill 是给淘宝/拼多多这类「标价 + 券 + 活动」的平台写的，输出的是人看的决策卡片，
不是机器执行的价格指令。Takealot 的采集结果区分最快配送与最低价位置，不能把所有报价混成一个
最低价目标，也不能把价格当成唯一决定因素。所以照抄它的规则表没有意义，但它**判断问题的方式**几乎可以整套搬过来。

下面写清楚：借了什么、丢掉了什么、落到代码的哪里。

---

## 一、借的是判断结构，不是规则表

| 竞价雷达里的东西 | 在 Buybox 模式下的对应物 | 落在哪 |
| --- | --- | --- |
| 决策卡片（判断/风险/置信度/动作/复查时间） | 每行一个 `plan`：方向、把握、风险、底价、上限、对手最低 | `automatic_pricing.plan()` → `rule.plan` → 界面「详情」 |
| 置信度 高/中/低（按数据完整度） | 能不能证明「谁在持位」+ 竞品报价是否带卡位类型 | `plan()['confidence']` |
| 风险等级 低/中/高/紧急（按竞品降幅） | 本店价与最低现货竞品的价差百分比；低于底价直接判高风险 | `plan()['risk']` |
| 毛利底线 `成本 ÷ (1 - 最低毛利率)` | `min_price`（系统 20% 利润底价，或人工填的固定底价） | `rule['min_price']` / `system_floor()` |
| 竞品分层（直接/低价扰动/锚点/品牌/替代） | 能抢走 Buybox 的现货 / 抢不走的缺货报价 / 抢不起的低价 | `_pools()` + `_winnable()` |
| 「竞品降价是否真实、是否持续、是否仍有毛利」 | 缺货报价不参与定价；低于底价的报价不参与抢位；同价不等于持位 | `_pools()` / `_winnable()` / `holding` 判定 |
| 缺失数据必须降置信度、不给确定性结论 | 采集失败、身份未核实 → 不动价，只记录原因 | `regime = blind` |
| 不绕过验证码/反爬/登录墙 | 被挡就停下来让人过验证，不改指纹不换 IP | 见第五节 |

丢掉的部分：优惠券、赠品、主图、客服话术这些「非价格防守」在 Buybox 里不存在——
购物车只有一个人能拿，没有第二个货架可以摆卖点。这部分不进代码。

## 二、两个方向，一条线：让利 vs 要价

> 抢价格的时候肯定是减少我的利润的；能自己持住价的时候，就要尽可能多要。

这句话拆开就是两套完全不同的规则，判错方向就是真金白银。所以 `decide()` 不再是一串
if，而是先判**方向**，再算价格：

```
有库存？ ──否──> off      无库存，跳过
   │是
采集到了？ ─否──> blind    证据不足，保持现价
   │是
我在持位？ ──否──> compete  抢位让利：只降不升，下限 = 利润底价
   │是
有现货竞品？ ─否──> scarcity 独家提价：没人能抢，按步长往上试，48 小时无成交且订单快照新鲜时回滚
   │是
                climb    守位提价：顶到「刚好还是最低」的位置
```

### compete（抢位让利）

- 只在 `target < current` 时才动，**永远不跟涨**。
- 下限是 `min_price`。够不着就明说「这个位置抢不起」，而不是硬降到亏损。
- **2026-10-23 更正**：同一卡位先取真实最低价，再判断领先差额是否满足底价。
  不能剔掉抢不起的最低价、改跟更贵报价并称为抢位；最低价仍在时，该位置并未变得可达。
  最快配送池不可达时仍可评估独立的最低价池；没有类型时只用一个合并池，不猜第二条赛道。
- 涨价与降价都遵守 `cooldown_minutes`。分步降价也必须等观察期结束，不能只限制守位涨价。
- `plan.target_lane` 记录本次目标（fastest / best_price / lowest），`target` 是尝试建议，
  并非持位成功证据；受降幅限制时明确写「分步接近目标」，实际效果等待新行情确认。

### climb（守位提价）

- 当前守位启发式会在竞品均更贵时**向下一现货竞品报价试探**：
  `target = 次低价 - lead_amount`，这是报价相对位置，不证明客户接受程度或涨价后仍持位。
- 上限三重夹：人工 `max_price`、`参考价 × (1 + raise_ceiling_pct)`、`raise_step_pct` 单步涨幅。
  默认 20% / 3%，可按 SKU 调。开 `smart_raise` 才走单步 3%，否则一次到位（仍受前两重夹）。
- 竞品报价是候选价依据，持位与利润效果仍需反馈验证。价格每次上移后下一轮会重新验证：如果我涨到 `次低价 - 1`，
  下一轮 Buybox 价 = 我的价，次低价还是那个数，`low - lead == current`，自然收敛停手。

### scarcity（独家提价）

- 触发条件：**持位 + 有报价但都不是现货**（竞品全缺货），或**只有本店在售**。
- 这两件事必须和「一条报价都没采到」分开。后者是证据缺失，`regime = hold`，不许动。
  旧实现把两者混在一起（`foreign` 空就当成没有缺货证据），结果是独家在售的 SKU
  永远不许涨价——把最大的定价权当成没有证据。
- 有回滚：试涨 48 小时无新成交，退回试涨前价格并暂停 24 小时。
  三个条件缺一不可（`automatic_pricing.plan()`）：试涨已满 48 小时、本店订单快照在
  2 小时内同步过（`sales_recent`，即 `operations_profile.synced_at` 距今 < 7200 秒）、
  且该 SKU 的最近成交时间早于试涨起点。订单快照过期时不回滚——判断不了这 48 小时里
  有没有成交，就不动价；`sku_last_sale_epoch` 缺失（从未记到成交）同样不回滚。

## 三、置信度与风险：界面必须说「我有多确定」

`plan()` 返回的 `confidence` 只由证据强度决定：

- **高**：持位已核实 + 至少 2 个现货竞品 + 报价带卡位类型（fastest / best_price）。
- **中**：持位已核实，或现货竞品带卡位类型。
- **低**：其余。低置信度时系统不会因为「价格刚好一样」就认为自己在持位。

`risk` 看的是「不跟价会怎样」：现货最低价已低于利润底价 → 高；价差 ≥15% → 紧急；
≥8% → 高；≥3% → 中；其余低。

这两个字段以前只存在于后端的 `last_result` 一句话里，用户只能从「按 PricePilot 现货
Buybox 规则调价」这种话里反推系统在想什么。现在 `plan` 整份落库，界面直接渲染。

## 四、为什么不做成 Codex 那种规则引擎

规则引擎的问题是：它只能回答「命中哪条」，回答不了「这次判断有多可信」。
而调价真正难的地方恰恰是后者——同一个「降到 262」，在持位已核实和身份未核实两种情况下，
后果完全不同。

所以这里的做法是：

1. **先算证据，再算价格**。`_pools()` 把报价分成能抢走 Buybox 的和抢不走的；
   `holding` 要求「同价」且「卖家身份已核实」；两者都不成立时直接 `blind`，不产生任何价格。
2. **每一步都能被反驳**。`plan.reason` 是人话，`plan` 里的每个数字都能在页面上找到来源
   （底价来自 `system_floor`，对手最低来自本轮采集，上限来自规则）。
3. **默认不动**。所有拿不准的分支都返回 `target = None`，保持现价。宁可少赚一次，
   不能在没有证据的时候改价——改价是写操作，写错了要人工核验才能恢复。

## 五、被网站验证挡住时怎么办（和参考 skill 同一条线）

竞价雷达自己的可信边界写着：不绕过验证码、登录墙、反爬、风控。这里沿用同一条线，
理由不是教条，是成本：

- 这个采集跑在**你自己的卖家账号**上下文里。解验证码、伪装指纹、换 IP 这类动作，
  赌的是平台风控识别不出来；赌输的代价是店铺账号被盯上，比一次采集失败贵几个数量级。
- 而且它不解决问题：验证是会话级的，绕过去一次，下一次还要绕。

实际做法（已经落在界面上）：

1. 采集器跑在**持久化 Chromium 配置目录**里（`BUYBOX_BROWSER_PROFILE`），验证过掉之后
   同一份 profile 里的会话对后台这一轮同样有效。
2. 被挡时 `error_code = site_challenge`，采集栏出现「人工过验证」按钮，直接落到
   「采集维护」面板：在真浏览器里把验证过掉，回列表点「立即采集」。
3. 后台不反复重试：`THROTTLED_CODES` 里的错误只把间隔拉长，不清 `next_due`。
   反复点「立即采集」不会恢复，只会多几条失败记录。

## 六、还没做的

- **变体匹配**：`9902390746609`（3 Pack）和 `9902415247821`（Nude - L）两条仍然是
  `variant_unmatched`。页面上确实有对应的变体按钮，但切换后的确认逻辑在这套 DOM 上不稳定。
  宁可拒绝报价，也不拿默认变体的价去调目标变体的价——那是直接算错钱。
- **销量反馈**：`scarcity` 的回滚依赖 `sku_last_sale_epoch`，目前只有同步到销售数据时才有值。
  没有它时试涨会一直涨到上限，不会自动回退。


## 2026-10-23：参考方法、落地范围和后续反馈

本次基线 `4a94d84cc2ad`，Codex 负责修复、CI、合并与部署；WorkBuddy 负责本机会话验收。

参考来源（2026-10-23 查阅，不安装或执行第三方代码）：

- [dynamic-pricing-ecommerce](https://github.com/nexscope-ai/eCommerce-Skills/tree/main/dynamic-pricing-ecommerce)：
  MIT；参考“可比较报价、经济底线、独立规则、冷却与回滚”的设计方法，不照搬推广段落。
- [takealot-plugin](https://github.com/tanaka-mambinge/takealot-plugin)：购物研究 skill，
  不是卖家调价算法，不替换现有授权采集会话。
- [genpark-dynamic-repricing-skill](https://github.com/alphaparkinc/genpark-dynamic-repricing-skill)：
  固定减价/涨幅只是示例，不把它当 Takealot 生产优化器。
- [Thompson Sampling for Dynamic Pricing](https://arxiv.org/abs/1802.03050)：后续数据充分时可研究
  有界候选价格的反馈学习，论文结果不等于本系统效果。

当前落实：目标卡位真实最低价可达性、涨跌对称冷却、建议与实际成功分开。
保留库存过滤、卖家/变体身份、行情过期保护、底价/上限、单次降幅、写入前暂停与并发保护。
未引入机器学习、未调整真实规则开关、未修改真实售价。

后续工作按证据推进，不一次替换整个引擎：

1. 记录价格生效时点、后续独立行情时点、对应目标卡位、配送位置与新订单，区分接口写入成功和持位成功。
2. 由真实日销与补货周期调整观察窗；慢销 SKU 不仅凭 48 小时无订单认定试涨失败。
3. 有可靠曝光/成交与库存记录后，以贡献利润而非持位次数评价候选价；低数据量仍使用可解释规则。
4. 再评估 Thompson Sampling 等学习方案，先离线/影子模式，不以真实写价做测试。

验证：新增 6 个无外部调用用例，旧版同池 R90/R115、本店 R120、底价 R100 得到 R114，
修复后保持现价；跨池仍可建议 R114。隔离加载实际决策函数通过新增 6 例和原有 11 例纯逻辑回归。
完整模块导入、写入并发与浏览器检查以最新 head 的 PR Check 为准；真实 SKU 反馈未验收。
