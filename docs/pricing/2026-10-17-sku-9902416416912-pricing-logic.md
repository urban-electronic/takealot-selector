## 1. 结论先说

**当前这一刻，这个 SKU 的正确操作是"不调价"。** 三条理由，都有数据支撑：

1. **它已经断货**：`stock = 0`，`status = Not Buyable`。`decide()` 第一行就是 `if stock <= 0: return None, '无库存，跳过'`——断货时降价抢不到 Buybox（没库存就无法成为 Buybox 卖家），涨价也没有意义。
2. **它在调价体系里是双重空白（API 形态）**：`GET /api/buybox` 对该 offer 返回 `monitor: {}`、`rule: {}`。注意：空对象只是 API 返回形态，**不足以证明数据库行缺失**（需直接查 `SystemSettings` 表确认，本文档不下此结论）；但可以确定的是"当前没有任何规则在消费这个 offer 的行情"。
3. **它没有任何可用报价**：`competitor_price = null`，无 snapshot，无 `own_price_asof`。按 `shared_snapshot()` 的逻辑，行情缺失即返回 `{'error': '行情缺失、失败或已过期', 'offers': []}`，`decide()` 直接保持现价。

所以本方案做三件事：**说清为什么现在不调、补上体系盲区、给出补货后的定价规则**。

> **v2 优先级说明**：按 Codex 评论 `6231834199`，调价方案部分暂不采纳、优先级后移；本轮优先任务是中文品名核查与确定项更正（见第 6 节）。Buybox 行情采集与调价规则是两套独立开关——没有调价规则时的行情采集**不构成浪费**，本文档不据此建议自动开关任何采集。

## 3. 诊断：三个发现

### 3.1 目标 SKU 的调价体系接入状态是空白（需修）

`start_worker()` 只枚举 `SystemSettings.key.startswith('_pricing_rule:default-store:')` 且 `enabled` 为真的行；`shared_snapshot()` 只读 `_pricing_monitor:{store}:{product_id}:{offer_id}`。API 对无配置的 offer 返回空 dict——**外观与"规则已保存但关闭"完全一样**。

v2 修正（Codex `6231834199`）：`monitor: {}` / `rule: {}` **只是 API 返回形态，不能据此断定数据库行缺失**——需后端直接查 `SystemSettings` 表才能确认。可以确定的只有：当前没有任何规则在消费这个 offer 的行情。Gold 变体属于"未接入"形态，用户会以为"它已经在管了"。

Silver 变体更隐蔽：monitor 行存在且数据每 30 分钟在更新（`status: success`，`last_success_at` 今天 08:29 UTC），但 `monitor.enabled = false` 且 rule 行不存在。**行情在采，但没有规则消费它。**

> v2 删去的论断：v1 称"采集算力花在了一个不会触发任何调价的 offer 上"（暗含浪费）。按 Codex 要求删去：Buybox 行情采集与调价规则按用户要求**共享行情但独立启停**，无 rule 时的采集不构成浪费，不据此建议自动关闭采集；是否建 rule 由人工决定。

### 3.2 竞品报价抓不全，会让 `follow_lowest` 永远看不到对手

Silver 的 `diagnostics` 显示：`http_status = 200`、`page_title` 正常、`buybox_cards = 1`、`variant_controls = 17`，但 `offers` 数组里只有自己的两条（`buybox` 与 `best_price`，都是 `isMine: true`）。同时快照里 `hasOtherSellers = true`。

**页面承认有其他卖家，解析结果里却没有他们。** 这会让任何 `follow_lowest` / `lead_amount` 策略退化成"永远保持现价"——不是不想降，是看不见对手。这是比定价参数更重要的问题。

### 3.3 两套毛利口径并存

`minimum_price_at_20_margin` 走**动态**口径（`success_fee` 随售价重算，已由 2.3 节复现），而 `profit_margin` 走**静态**口径（直接 `(actual_sale_price_zar − total_cost_zar) / actual_sale_price_zar`，R284 → 51.83%，与系统记录一致）。

后果：若调价判断引用 `profit_margin`，会**高估**降价后的毛利（没算佣金随之下降的部分）。方向上是保守的（偏安全），但 `minimum_price_*` 与 `profit_margin` 对同一售价会给出不同结论，评审时容易各说各话。建议在文档与 UI 上标明口径，或统一到动态口径。

## 4. 调价逻辑设计

在现有 `decide()` 之上补齐，分五层。**L0 一票否决，任何配置都不能覆盖。**

### L0 闸门（一票否决，不可配置覆盖）

| 条件 | 处置 | 现状 |
| --- | --- | --- |
| `stock <= 0` | 不调 | 已有 |
| 报价缺失 / 失败 / 过期（`shared_snapshot` 返回 error） | 不调 | 已有 |
| 卖家身份核对失败（`offer_id` / `sku` 不匹配） | 不调并暂停 | 已有 |
| 变体切换失败 | 不调，不落 competitorOffer / buyboxPrice，不刷 `offersFetchedAt` | pricepilot `hasUsableQuote()` |
| `boundQuoteAt` 与决策时报价不一致 | 不调，reason 含"报价版本已变化" | pricepilot |
| **低于 20% 毛利硬底** | 不调 | 已有（`use_system_min`；硬底口径见 2.3 节） |

### L1 价格底线

- 硬底：`ceil(minimum_price_at_20_margin)` = **R138**（对系统字段取整；若后端改为对计算值直接 ceil 则为 R139，口径差异见 2.3 节警示，需后端统一）。任何 `target < 硬底` 一律放弃。
- 软底：`minimum_price_at_15_margin` = R128，仅在商品被打上"呆滞清货"标记且**人工单独开启**时允许；不允许作为常规调价下限。
- 若 `minimum_price_at_20_margin` 高于人工 `max_price`，报错暂停（已有），不得静默取其一。

### L2 方向判定

- **未持有 Buybox** → 只降不升（已有）。
- **持有 Buybox**：
  - 存在现货竞品且最低价 < 我方 → 目标价 = `max(floor, 竞品最低价 − lead_amount)`。
  - 无现货竞品 → **不降价**。没有对手就没有降价理由；仅在 `smart_raise` 且确认竞品为 `pre_order` / `backorder` / `out_of_stock` 时按现有 scarcity 逻辑试涨（每次约 3%，累计不超过参考价 20%）。
  - 试涨 48 小时无新成交 → 回退试涨前价格并暂停 24 小时（已有）。

### L3 幅度与频率护栏（建议新增）

现有代码只有 `min_change`（变化小于阈值不动）与 `max_daily_changes`，缺少对**幅度**的约束。建议补三条：

1. **单次降幅 ≤ 5%**：`target >= current * 0.95`。防止一次跟价到底。
2. **24 小时累计降幅 ≤ 10%**：按 `history` 回溯 24 小时窗口求和，超出则本轮不动。
3. **涨价单次 ≤ 3%**，与现有 scarcity 试涨幅度保持一致（已是事实标准，显式写进规则）。

### L4 同链接多变体协同（本品关键）

同一 `PLID` 下多个 SKU 时：

1. **变体间价差 ≤ 10%**。Gold 与 Silver 现差 R3（1.5%），合规。若某一变体被单独降到使价差超过 10%，应触发提示——否则买家会全部流向便宜变体，贵变体库存沉淀。
2. **断货变体不参与定价，也不因自己断货而涨价**。`decide()` 的 scarcity 分支判断的是**竞品**缺货，不是自己缺货；这一区分必须保持，否则"没货反而涨价"会在补货后丢 Buybox。
3. 变体切换必须走身份核对（`official_offer` 已校验 `sku`），不得用页面价直接跨变体套用。

### L5 观测与回退

- 每次调价落 `history`（已有，保留 50 条）。
- 连续 N 轮（建议 3）未持 Buybox 且未成功调价 → 自动暂停并提示人工介入，避免无限空转。
- 平台 PATCH 返回非 200/202 或含 `validation_errors` → 暂停并提示核对（已有）。
